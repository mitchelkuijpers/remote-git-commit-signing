# 0002: GitHub release is the canonical artifact source; the signer's dist directory is a refreshed cache

The v0.1.0 release was cut by hand from a recipe documented only in the README, and its assets were never attached — the release exists with zero assets, so `deploy/install-client.sh`'s release-download path fails and the signer's `SIGNER_DIST_DIR` (populated separately by `install-server.sh` from a repo checkout) is the only working binary source. Meanwhile the GitHub instance (`github.int.exe.xyz`) rejects anonymous requests, so a fresh agent VM cannot download release assets at all: provisioning must keep flowing through the signer's `/v1/client/...` endpoints behind the peer integration, which need no credentials.

We made the GitHub release the canonical artifact store and the signer's dist directory a cache refreshed from it: a release workflow (`.github/workflows/release.yml`) cuts releases on `v*` tag push — or manual dispatch naming a tag — runs the test suite, builds the artifact set with the single canonical recipe (`scripts/build-release.sh`), and publishes immediately (no draft gate; the download path is checksum-fail-closed). The artifact set now covers everything `install-client.sh` advertises: client tarballs and raw binaries for linux/darwin × amd64/arm64, plus linux server binaries. Agent VMs were deliberately **not** pointed at GitHub releases: that would couple the one-liner to GitHub credentials being present on every VM.

## Consequences

- The artifact-name contract (tarball names, raw-binary names, `checksums.txt` in exact `sha256sum` format) is pinned by `scripts/build_release_test.go`, because `install-client.sh` looks entries up by exact filename and the signer's bootstrap downloads the raw linux binaries — a rename anywhere would break the one-liner silently.
- Refreshing the signer's served client after a release is an explicit operator step (`gh release download vX.Y.Z --pattern 'git-remote-sign-linux-*' --directory "$SIGNER_DIST_DIR"`), so the dist directory can now skew from the server version until refreshed; `install-server.sh`'s same-tree build remains the skew-free initial deployment.
- `install-client.sh`'s default `GIT_REMOTE_SIGNER_RELEASE_VERSION` stays pinned to `v0.1.0` and must be deliberately bumped per release; the signer-rendered `/install.sh` path is unaffected (it serves `GIT_REMOTE_SIGNER_BIN` from the dist directory).
- Dispatching the workflow against an existing tag replaces that release's assets (`gh release upload --clobber`), which is how v0.1.0's missing assets get backfilled.
